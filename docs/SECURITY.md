# Security and release gate

Implemented: server-side authentication and owner checks, trusted server admin UUID allowlist, asymmetric JWT issuer/audience/
expiry/role checks, strict input/output validation, bounded bodies, allowed upstream hosts/paths, no arbitrary redirects,
shared request quotas, private raw storage, immutable hashes, safe XML/ZIP parsing, synthetic production guard, security headers,
raw attachment delivery, audit trails, consent-based analytics and privacy-aware error reporting.

The production configuration refuses SQLite, demo mode/admin, demo auth, local raw storage, wildcard allowed-host settings and
non-HTTPS allowed origins. Set exact hosts and origins. A Supabase service key belongs ONLY in server secret storage.
Never put provider secrets, storage service keys, JWT secrets or PostgreSQL URLs in NEXT_PUBLIC variables.

JWT verification uses asymmetric Supabase signing keys. Projects still using legacy symmetric signing must migrate signing
configuration rather than adding an unreviewed HS256 acceptance fallback. OAuth provider credentials and redirects are configured
in Supabase/Google, not generated by this application. Admin status is never taken from user-editable metadata.

RLS protects client roles, while the backend uses a trusted connection with explicit owner checks. Initially one default watchlist
and portfolio are provisioned per user. Frozen migrations revoke default privileges; test with actual role sessions before beta.
Application account deletion and Supabase Auth user revocation/deletion are separate operations. Deleting only app data allows
subsequent sign-in to create a blank profile. No self-serve account-deletion UI is claimed.

## Residual risks / checks before public deployment
Browser sessions use Supabase PKCE local storage. XSS can still compromise a browser session. Current static Next CSP permits
inline hydration/styles and is not a nonce-based strict policy. Review nonce/session transport alternatives during security QA.
No claim that this software is unhackable. Run dependency audits on the actually installed lockfiles and inspect relevant advisories.
Conduct browser/mobile E2E, role-based Postgres tests, SSRF/boundary review, realistic document load tests, backups/restore tests,
credential rotation, provider outage simulation, long-running lease tests and operational cost alerts.

Verify bucket privacy and persistence across worker redeploys. Preview/production origins must not allow arbitrary attacker sites.
Finish the deployed privacy notice, operator contact, retention schedule and consent/cross-border processing disclosures appropriate
to the actual service. The placeholder privacy page is not a finalized legal policy.
No paid resources or production changes were executed in this delivery.
